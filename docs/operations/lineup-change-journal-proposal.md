# Draft: lineup change journal

Status: design only. This is not an implemented cache contract or approval to merge, migrate, or deploy. The current #1400 prototype performs a full selection and content fingerprint on every request; it can increase database traffic compared with a remote cache hit. A low-cost freshness token needs the guarantees below before it may be used.

## Scope and invariant

A token must distinguish every committed change that can affect `getCurrentStatsSelectionInTx` or the nine fields returned by `getLineupStatsPopulation`. It may change for irrelevant writes; in that case a fresh selection and row-content fingerprint can still find an unchanged population. It must never remain equal after an unrecorded relevant change. The selection, its content fingerprint and any aggregate on a miss run in one repeatable-read, read-only snapshot. A token read and a cache hit must correspond to the same statement snapshot, not an earlier transaction's uncommitted view. An unavailable, malformed, oversized, or untrusted token causes the existing canonical uncached read, never a stale hit.

The proposed coverage includes `matches`, `seasons`, `match_maps`, `match_player_stats`, `match_demo_imports`, `match_demo_stat_projections`, `match_rosters`, `match_roster_players`, `event_roster_members`, `users`, `steam_profiles`, `user_gameplay_steam_ids`, and conservatively `competition_entries`. This list must be independently checked against the current selection, evidence revision, roster and identity owners and every joined leaderboard expression. All inserts, updates, deletes and truncates must be covered, including writes by the previous application version, bulk paths, operator corrections and cascades. Statement triggers are conservative and may record an update that does not change the effective selection. A future schema or query change must update the dependency contract before use.

## Candidate protocol

- A private journal has a random epoch, an append-only event UUID per relevant committing transaction, and a compacted summary. A trigger runs in the writer's transaction. It deduplicates on epoch and the **top-level transaction ID**, so multiple affected statements produce one event. A rolled-back transaction contributes nothing. The event UUID must be generated inside the trusted trigger; application roles cannot supply, update or delete it. Index partitioning by a deterministic hash of transaction ID can spread insertion contention. This design does not update one global revision row in each user action, although normal PostgreSQL index and WAL contention remains.
- A token contains epoch, total event count and a 256-bit commutative digest of event UUIDs, combining the compacted summary and currently visible events. For example, the digest may be the XOR of SHA-256 of each random UUID. It detects out-of-order commits without relying on sequence allocation order. It has a cryptographic collision assumption and is not mathematically collision-free. A plain count, `MAX(id)`, timestamp, XID maximum, or sequence value is insufficient across divergent histories and out-of-order commits.
- Readers obtain the entire token in one SQL statement. Once its snapshot is fixed, a commit after that snapshot is legitimately not visible to this read but must change a later read's token. A process-local bounded cache uses the token and exact match/cutoff descriptor, and does not share entries across unverified database namespaces. A changed token causes a fresh canonical selection and row fingerprint; identical qualifying content can reuse the population without reaggregating.
- For rolling cutoff, store the fill's application time and, from the same snapshot, a conservative earliest future completed-match timestamp. Reuse only while the current application time has not moved backwards and has not crossed that boundary. If the boundary cannot be established, bypass the fast path. Fixed historical cutoff must remain exactly the requested value. A conservative extra expiration is safe; missing a boundary is not.

## Compaction, availability and bounds

A background compactor selects only committed events visible in its own snapshot, removes a bounded batch with `DELETE ... RETURNING`, and combines their count and digest into the summary **in the same transaction**. Thus readers see either the pre- or post-compaction state and obtain the same token. A writer committing after the compactor snapshot remains in the live journal. Compactors must serialize only with each other, for example using a nonblocking transaction advisory lock; request and business-write transactions must not acquire it. Lock waits and batch work need strict limits. Transaction retries must not double-apply a batch.

The live journal cannot be purged, truncated, or dropped while any cache depends on it. A bounded read may inspect at most a configured number of live events; an overflow or compactor failure bypasses caching and alerts rather than losing events or blocking business writes. This does not itself bound disk growth during a long compactor outage: storage monitoring, alert thresholds, recovery procedure and a safe operator response are required before enabling the feature. The compactor must not remove any event without atomically incorporating it in the summary.

## Migration, permissions, restore and rollback

The migration must establish an epoch and triggers before a compatible application enables the fast path. Creating triggers requires table locks; set bounded lock timeouts and abort the migration rather than wait indefinitely or take shortcuts. Previous application writers continue to be covered at the database boundary. Deny direct event or summary mutations to application roles. If trigger writes require a `SECURITY DEFINER` function, use an owner with only necessary grants, a fixed safe `search_path`, qualified object names, and revoke direct execution as appropriate. Keep journal data opaque and expose neither raw events nor internal tokens to public Data APIs. No new credential is required by the design, but the existing runtime role and Supabase grants/RLS must be verified.

A full atomic restore of the same journal and all dependent business tables can represent the same historical dataset. A fork or restore must establish a **new epoch before accepting any writer or fast-cache read**. Writers must be quiesced during rotation; otherwise an in-flight transaction could append to the old epoch after the switch. Partial restores, a missing journal, disabled triggers, an unverified role, or ambiguous database namespace must disable the fast path and require a fresh baseline. Restoring old backups without journal tables must also remain safe.

This is not implemented by the current restore owners: `scripts/db/recovery/restore.ts` and `scripts/db/preview/refresh.ts` truncate and import with `session_replication_role = replica`, bypassing ordinary triggers. Recovery, Preview and relocation owners need explicit, verified epoch initialization and a gate before any cutover. A trigger-only migration is therefore unsafe. Rollback to an older application must leave capture active while journal consumers exist; re-enabling after capture has been removed or bypassed requires a new epoch. Migrations follow the repository's forward-only chain. No runtime or recovery privilege may be silently expanded.

## Acceptance and measurement still required

Before code is eligible for review, prove actual table coverage and source ownership; validate transaction-ID deduplication, out-of-order commit, abort, cascading writes, no-op writes, truncate, in-flight compaction, compactor interruption and overflow against real PostgreSQL. Rehearse old and current full backups, partial restore rejection, replica-role import, epoch rotation with blocked writers, pool replacement, primary/standby switch and rollback in isolated environments. Verify the row-fingerprint SQL against the canonical leaderboard for changes to scores, statistics, identity grouping, replacements and deletions, with historical and rolling cutoffs. Existing CI passing alone does not establish these cases.

Measure end-to-end traffic and latency using comparable workloads: the existing remote warm hit has zero DB reads, while this design has at least one token SELECT per read and adds writes, index/WAL, compaction and occasional full selection. Measure actual fill/key overlap and selection metadata bytes, plus insert throughput, journal growth, compaction load and p95 latency. The available 2026-11-01/02 observation does not identify the retained lineup query shapes or establish cache hit rate, and is not a provider billing measurement. Do not claim a net saving or the daily budget target until measured.
