## 1. 范围、事实等级与阅读边界

RivalHub 的公开定位是高校电竞赛事运营平台，当前主要业务围绕 CS2、NJU Rivals 与 NJU Major，覆盖参赛准备、组队、报名审核、赛事运行、单场赛务、观赛参与和历史数据。README 声称 2026 NJU Rivals 已经完整运行；本轮没有独立核验这项运营历史。官方实例是当前支持重点，第三方 production self-hosting 不属于 2.x 的正式支持目标。[E01](implementation-index.md#e01)

本文采用四种明确分类：

| 分类 | 含义及适用边界 |
| --- | --- |
| **政策要求** | 已发布赛事规则明确要求，适用于对应赛事和规则版本；不自动外推给所有赛事。变更需要赛事治理决定。 |
| **业务契约** | 当前实现与领域契约共同保护的业务含义，例如历史不能被当前队员资料重写、不同权限看到不同信息。要保持现有业务正确性就必须满足；并不表示用户已经决定未来永远沿用所有现行规则。 |
| **实现选择** | 当前可观察行为、固定参数、算法、权限粒度或技术/交互安排。需完整理解其影响，但不能仅因现有代码如此就认定未来必须复刻；未找到理由时不补造理由。 |
| **未知或差异** | 尚无证据、未现场验证、资料相互不一致，或政策允许范围大于系统支持范围。集中记录于第 11 节。 |

以下流程不是未来页面清单。表格里的“场景”指现有能力能够完成的任务，不是访谈证明的动机、痛点、频率或优先级。没有证据支持付费意愿、留存目标、增长目标、某类用户占比或既有页面的设计理由。

## 2. 用户、职责和业务场景

一个人可以同时承担多个职责；“观众”“选手”“队长”“裁判/解说”不都是独立账号角色。[E02](implementation-index.md#e02)

| 业务身份 | 现有任务与触发场景 | 权限、责任与边界 |
| --- | --- | --- |
| 匿名访客/观众 | 查公开赛事、公告、规则、参赛队、比赛、公开选手/队伍档案与统计；观看符合条件的 LIVE；进行本地赛事推演；提交反馈 | 不能代参与者报名、投票、提交正式预测或写赛果。可凭链接看测试赛不等于测试赛保密。 |
| 登录用户/选手 | 维护本人资料、教育认证、竞技档案；找队、接受邀请；个人报名或确认代表一队参赛；查看自己的报名与比赛待办；参与观赛活动 | 参与资格还取决于邮箱、资料、名单、窗口和纪律状态；已登录不等于已获参赛资格。 |
| 长期 Team 队长 | 创建/维护队伍、邀请与管理成员、交接队长、管理招募；为队伍创建当届报名 | 长期队长与当届赛事负责人是两个事实。创建报名时由队长负责，之后当届负责人可独立交接。 |
| 当届赛事负责人 | 编辑本届名单、指定预定主力、提交/撤回审核、申请名单变更、交接当届责任；协商比赛时间、提交首发 | 不能替普通成员作参赛确认；不能通过长期队伍变动绕过冻结名单。普通成员退出本届与退出长期队伍分别处理。 |
| 本场 BP 负责人/测试操作人 | 赛前准备确认、禁选地图和选边；技术超时申诉 | 正式比赛 BP 负责人来自本场首发；测试赛可另指定账号。轮到本队且具备本场操作资格才可写入。 |
| 本届赛事管理员/办赛方 | 审核报名和政策例外；确认赛前名单、种子与阶段；处理排期、比分、纠错、纪律、荣誉、社区奖；管理公开信息和本人授权设备 | 权限限于获授权赛事。教育原始证据审核、全局用户治理等不因赛事管理权自动获得。 |
| 裁判/解说/制播执行人员 | 认领比赛、按名单和 BP 在外部平台建房、核对身份、监控现场数据、录分、补齐计分板和录像/Demo | 代码复用赛事管理员授权与解说登记，每场最多两人；没有单独“仅裁判/仅解说”最小角色。认领不证明已开播。 |
| 超级管理员/平台运营 | 新建、配置、发布赛事；管理用户、管理授权/邀请、教育审核、竞技目录和换算政策、全局公告/反馈/审计与调度恢复 | 可跨赛事管理；平台故障和授权问题由此类人员处理。授予赛事管理与修改全局角色不同。 |
| 赛委会 | 正式规则解释、特殊参赛例外、违规和影响已开赛后续比赛的事故裁决 | 这是政策与人工运营责任，不是代码中独立账号角色或已经自动化的审批系统。 |
| Mizar、DAK 等外部工具 | 经授权取得赛事范围数据，分别处理现场实时数据/可靠事件、赛后 Demo 证据上传 | 是机器调用者，授权人和机器执行者分别留痕；不等同于拥有所有管理员权限的人。 |

账号权限当前只有普通用户、超级管理员两种全局角色，另有按赛事授予的管理权。成员、队长、负责人和机器授权必须从各自当前关系判断，不能靠界面入口或历史报名推定。本人私有参与记录、管理员内部证据与公开信息分别授权。[E02](implementation-index.md#e02)、[E24](implementation-index.md#e24)

## 3. 需要分别理解的业务对象

| 对象 | 回答的问题 | 必须区分的相邻事实 |
| --- | --- | --- |
| 人与登录凭据 | 是谁；用什么方式证明身份 | 一个人可绑定多个已验证邮箱；账号归并不等于普通凭据绑定。Steam 游戏身份也不等于登录凭据。 |
| 长期资料 | 此人现在声明什么、有哪些教育与竞技事实 | 单届报名时的自述、当届资格与比赛当时记录保留各自历史。 |
| 长期 Team | 目前及历史上谁属于这支组织 | 不从属于某一届赛事；当前成员不等于当届名单。 |
| 当届参赛方 | 哪一队/哪一组选手参加这一届 | 可来自长期 Team，也可由 Rivals 选秀产生而没有长期 Team。审核通过还不等于取得 Major 正赛席位。 |
| 名单版本与本人确认 | 哪一版名单正在编辑、已提交、已批准；谁确认参赛 | 提交者、参赛成员、审核者各自的事实；撤回审核不解除成员承诺。 |
| 正式赛事名单 | 本届当前可以选择哪些出场成员 | 冻结后的名单不能被长期组队变动静默覆盖；过去被比赛引用的成员记录继续保留。 |
| 单场阵容 | 这一场实际上确认哪些首发、谁负责 BP | 从合法本届名单选取；不是把预报名十人当作实际出场十人。 |
| 赛事与阶段运行 | 一届比赛如何组织；某阶段按哪批名单、种子和规则运行 | 计划阶段不等于已启动阶段；资格赛、正赛运行、最终结果分别成立。 |
| 比赛、地图、实际开始、正式结果 | 一场系列赛的执行、逐图回合比分和最终地图胜数 | BP 开始、实际游戏开局、显示中的系列进度、最终系列比分不是同一个状态。 |
| 统计、LIVE、推演、荣誉 | 正式事实的统计/实时观察/假设选择/颁授决定 | 统计与显示不能反过来改赛果；社区奖、单场 MVP、官方荣誉和预测纪念币分别存在。 |

这些分离属于当前业务契约。改名、换人、目录更新、账号解绑、归档不能无痕重写已经冻结的赛事依据。当前长期 Team 改名会同步到尚未结束/归档的关联参赛方；已结束赛事保留原名称，所以“任何赛事显示名都不变”也不准确。[E03](implementation-index.md#e03)、[E06](implementation-index.md#e06)、[E09](implementation-index.md#e09)、[E11](implementation-index.md#e11)

## 4. 参赛之前：账号、资料、认证与组队

### 4.1 账号建立与恢复

现有路径为邮箱/密码注册 → 验证邮件 → 明确确认 → 建立应用登录；普通登录、忘记密码/邮件找回、改密、退出均有入口。注册响应本身不证明已成功建号或登录，账号服务不可用和凭据错误有不同结果；对外不泄露邮箱是否注册。[E03](implementation-index.md#e03)

用户可绑定/撤销备用邮箱。绑定的身份已经属于另一个账号时，需要证明两边控制权、选择保留账号并查看归并影响；存在 Steam 冲突、队伍时间线/负责人冲突、重复正式比赛事实等不能无歧义处理的问题时拒绝归并。保留账号的个人/竞技资料保留，另一账号的竞技资料删除；其他可归属历史和身份按归并规则处理，来源与操作人历史保留。有待归并账号的 BET 账户时目前也阻止归并。[E03](implementation-index.md#e03)、[E20](implementation-index.md#e20)

当前登录有效期为 30 天（实现选择）。退出使本次会话失效；改密、找回、撤销备用凭据及归并会撤销相关旧会话。密码更新结果不确定时阻止新登录颁发，交平台运营核实后恢复；不能将“页面提示成功”当作跨服务修改已经一致完成。没有自助设备列表或通用账号删除产品。[E03](implementation-index.md#e03)、[E24](implementation-index.md#e24)

### 4.2 教育与竞技资料

**政策要求（Major）**：注册、邮箱验证、高校身份认证，填写展示昵称、实际比赛使用的 Steam64、完美平台身份、QQ 和所需历史/近期段位及 Rating；正式名单 5–9 人，名单与每场 5 名首发中都至少 3 名南京大学成员。外校成员允许参赛；最强外校成员与最强南京大学成员的历史实力差距原则上控制在 3 星，特殊情况人工复核。按当届冻结规则判断，不能推广成所有赛事的门槛。[E01](implementation-index.md#e01)、[E05](implementation-index.md#e05)

教育认证有三条现有路径：[E04](implementation-index.md#e04)

1. 已验证邮箱精确命中启用的学生邮箱目录，立即产生在读认证；并非任意 `.edu.cn` 邮箱均可，也不强制替换当前登录邮箱。
2. 提交学信网学籍/学历报告验证码，超级管理员人工核验。
3. 新生选择目录中的高校并提交一张录取通知书图片，人工核验在读身份，不证明毕业身份。

人工认证区分待审、通过、驳回；同一待审/通过主张重复提交可复用结果，被驳回后重提形成新记录，保留旧审核。教育结论与证据分别保存。审核完成满七天后证据到期，新的读取/签名拒绝；清理失败可重试，认证结果和审核历史不因此删除。待审材料没有已定义的统一放弃清理期限。[E04](implementation-index.md#e04)、[E24](implementation-index.md#e24)

竞技档案当前支持完美平台与 5E，各自拥有赛季、段位、星数和 Rating 语义。未填写、明确未定级、已定级是不同事实。跨平台按版本化换算统一参考尺度，不把 5E Rating+ 当成完美 Rating Pro。新赛事使用换算后更强的有效记录；历史冻结规则可能保留旧选择语义。Major 参考按历史最高 50%、前一完整赛季 20%、最近完整与当前赛季较高记录 30% 计算；队伍参考只用五名预定主力平均值，不代替最终人工种子。[E05](implementation-index.md#e05)

**实现选择**包括未定级估算、精确强度轴、同分处理和展示映射；估算必须保留来源，不成为用户真实申报。全局换算政策由超级管理员克隆草稿、校验、批准、设为当前或退役；赛事实际开放报名时冻结需要的目录与换算上下文，之后全局变更不重解释该届。[E05](implementation-index.md#e05)、[E07](implementation-index.md#e07)

打法/风格、比赛经历、地图熟练度属于长期声明；个人报名会保存当届快照。地图“未声明”不等于明确“不熟悉”，报名位置也不等于正式比赛中经过证明的战术角色。[E03](implementation-index.md#e03)、[E17](implementation-index.md#e17)

### 4.3 长期 Team 与招募

现有流程为创建队伍 → 邀请已有用户或发分享邀请 → 对方接受/拒绝 → 成员管理/队长交接；队长可维护名称、简介、Logo，调整活跃/替补状态、移除成员；成员可退出。当前一个人不能同时有两份未结束的长期队伍成员关系，队长须先交接才能退出；有未结束赛事参赛条目的队伍正常路径不能直接解散。邀请会过期或被撤销，接受邀请不自动确认某届参赛。[E06](implementation-index.md#e06)

队长发布招募、选手发布求队意向；浏览者可筛选和表达/撤回加入意向，队长可处理意向。意向不建立成员关系，仍需正式邀请。目标可为某赛事或不限赛事；选中赛事时兼容展示该赛事和不限赛事意向。招募有有效期和目标赛事窗口约束，报名未开放时可能已能招募；能公开招募不保证某一队此时能修改赛事名单。招募不是私信或即时聊天能力。[E06](implementation-index.md#e06)

## 5. 赛事建立与参赛流程

### 5.1 共同的赛事生命周期

当前赛事可用 Rivals、Major 或自定义模板建立。模板给默认能力，业务按保存的报名模式、选秀/投票/社区奖能力、名单规则与阶段计划运行；展示名称不能用来推断所有行为。自定义赛事的通用阶段执行器支持循环、双败、单败；Swiss 由托管 Major/Qualification 的特定规则运行，自定义模板存在不等于任意人数与赛制组合均被支持。[E01](implementation-index.md#e01)、[E07](implementation-index.md#e07)、[E11](implementation-index.md#e11)

赛事草稿 → 发布 → 等待/实际开放报名 → 按赛事能力组织参赛与比赛 → 完赛 → 归档。**发布、计划开放、实际开放、报名截止、名单锁定、计划正赛开始、实际阶段开始分别是事实。** 已发布可能仍未排报名时间、尚未到时或待系统补开；截止后不能因“曾开放”继续提交。提前开放需要明确操作并更新有效计划时间；实际开放完成所需资格上下文冻结。草稿撤回/删除受已有业务历史保护。[E07](implementation-index.md#e07)

Major 报名截止不会自动开正赛，计划开始时间到达也只产生待处理状态。**个人报名不同**：已实际开放且通过人数达到容量或截止到期时，调度或审核路径可自动推进至投票（未启用投票则至比赛阶段）；这是当前实现，不能遗漏或套用 Major 说明。原文档存在冲突 C01。[E07](implementation-index.md#e07)

### 5.2 Rivals：个人报名、队长投票与选秀

| 环节 | 当前流程及结果 | 阻塞/分支 |
| --- | --- | --- |
| 个人报名 | 登录后按本届配置填写身份、联系方式、Steam/完美资料、位置、竞技记录、地图熟练度、自述、队长意愿和反作弊承诺；可保存草稿后提交 | 未到窗口/截止、容量、身份类型、段位和字段校验等不满足则拒绝。长期资料与本届自述快照分开。 |
| 审核 | 待审 → 通过/拒绝/候补；管理员按允许阶段补正状态 | 拒绝与候补不是已入选；审核状态可变更范围受赛事阶段约束。 |
| 队长投票 | 已通过者向本届已通过且愿意当队长者投票；投票期间可撤票 | 当前最多 3 票，不可投自己或重复投同一人。管理员确认 8 名队长；按票数、最高 Rating、报名先后排序，且有最低总票数门槛。 |
| 蛇形选秀 | 建立赛事原生参赛方；8 队、6 轮，每轮反转顺序，队长选尚未分配的合法选手 | 前 4 轮为首发、后 2 轮为替补，队长已占首发位；同主位置每队最多 2 人，单轮 180 秒；超时按既定竞技排序与位置空缺策略自动选人。 |
| 比赛与收尾 | 选秀结果与本届名单一致落地；默认 8 队循环排位赛后双败淘汰，常规 BO3、决赛 BO5（排位赛 BO1） | 具体运行读本届阶段计划；成绩、统计、荣誉与归档分别处理。 |

上表中的人数、投票限额、选秀时间与自动选择算法是此基线的默认/固定实现；没有证据证明它们是未来设计必须保持的普遍用户要求。选秀提交需防重复与并发冲突，暂停/恢复、管理员代操作和超时处理不能形成重复选人。[E08](implementation-index.md#e08)

### 5.3 Major：队伍报名到审核通过

1. 长期队伍队长在开放窗口创建本届参赛方，指定本届名单与五名预定主力；新选择成员来自当前长期队伍。
2. 每名成员本人确认或拒绝参赛。确认会占用本届唯一有效参赛承诺；不同赛事的参赛分别管理。
3. 系统检查资料、教育/竞技资格、人数和队伍构成；负责人提交审核。管理员只能解除被明确标记为可豁免的政策限制并记录理由，不能“强行通过”缺身份、未确认或不完整资料；特批绑定本次名单版本和资格事实。
4. 管理员批准、候补、拒绝或要求补正。补正与再次提交保留原记录；批准形成获批版本，但只是正赛候选资格。
5. 提交窗口仍开放时可撤回审核，生成同一参赛方的新草稿，不释放成员承诺；截止后继续待审。草稿没有普通“终止报名”动作，状态名中的已撤回不能一概当作这项撤回审核。
6. 获批后在允许窗口内申请名单变更或由已确认普通成员本人退出本届，形成新草稿并重新检查、确认、审核。负责人先交接才能退出；冻结或窗口关闭后联系管理员，不能由普通自助操作绕过。[E09](implementation-index.md#e09)

### 5.4 Major：资格方案、Play-in、最终名单与种子

报名截止且审核/补正/候补处理完毕 → 冻结合格候选范围 → 保存预排名/资格方案草稿 → 确认方案 → 必要时进行资格赛 → 确定正赛参赛方 → 最终名单调整与复审 → 统一冻结名单/参赛方 → 生成不可变系统种子建议 → 人工确认最终种子 → 明确开赛。[E10](implementation-index.md#e10)

**业务契约**：报名通过、资格预排名、直通/资格赛晋级、正赛席位、冻结名单、系统实力建议和最终种子不能相互替代。管理员不能任意替换系统推导的晋级者来补人数。没有足够合法队伍时保持阻塞，不能用空队/假名单补齐。[E10](implementation-index.md#e10)

**当前支持范围**：托管 Major 支持 24 队或 32 队，默认 32；24 队有两阶段 Swiss，32 队有三阶段 Swiss，最后均为 8 队单败 Playoffs。超额报名资格赛支持镜像种子 Direct BO3 或 Short Swiss（2 胜晋级、2 负淘汰、最多 3 轮；Play-in 队数须为 4 的倍数）。候选数超过正赛容量两倍时单层资格赛不支持。政策允许的资格赛形式更宽，不能承诺分组循环资格赛已经实现。[E01](implementation-index.md#e01)、[E10](implementation-index.md#e10)、C04

资格方案确认前可以保存/调整预排名；确认必须基于最新已保存版本和未变化的候选/容量。确认后锁定，首轮生成前可明确重置。每轮先预览再确认对阵，结果写入正式比赛后由管理员明确生成下一轮，不因单场结果自动创建下一轮。[E10](implementation-index.md#e10)

报名截止和资格赛期间自助名单调整关闭；资格赛完成后，仅最终正赛参赛方在最终截止前重新开放调整。政策允许参加过 Play-in 的选手加入新的正赛队；系统仍要求释放原有效承诺、满足队伍/名单关系、重新确认与审核，不能同时占两支正赛队。最终冻结产生实力建议快照；后来改档案、看另一种排序或调人工种子不重算旧建议。[E09](implementation-index.md#e09)、[E10](implementation-index.md#e10)

### 5.5 阶段运行与正式收尾

每个正式阶段以启动时的参赛方、种子、规则和资格上下文运行。Major 正赛 Swiss 每阶段 16 队，3 胜晋级、3 负淘汰、最多 5 轮；从已确认比赛结果生成同战绩配对并处理重赛限制，轮次/阶段确认后派生晋级与下一阶段。默认 32 队方案由 17–32 号种子先参赛，再分批加入其余高种子；24 队方案由 9–24 号种子先参赛，再加入前 8 种子。阶段可以全程 BO3；使用 BO1 的阶段，晋级/淘汰关键战仍为 BO3，Swiss 不接受 BO5。淘汰赛胜负关联后续对阵。对阵表、积分榜和首页摘要都是读取结果，不能手工改摘要代替正式推进。[E01](implementation-index.md#e01)、[E11](implementation-index.md#e11)

已发布 Major v1.1 §8 允许季军赛与并列季军两种方案。当前由管理员在启动 Playoffs 时选择是否设置季军赛，选择在淘汰赛创建时冻结。启用时，两支半决赛失利队进行 BO3，以赛果确定第 3、4 名；未启用时，不增设季军赛，两队并列第 3–4 名。启用季军赛后，决赛与季军赛都必须完赛并具有有效正式比分，才能生成待确认的最终结果。[E11](implementation-index.md#e11)

Major 最终名次先待确认，管理员确认后才可作为正式荣誉依据及归档前提。取消某人的资格、改判比赛、撤销荣誉和替补授予必须分别明确决定，不自动连锁。不同赛事/历史阶段的精确 BO 与名额读其冻结计划，不能拿当前默认值反推过去。[E11](implementation-index.md#e11)、[E22](implementation-index.md#e22)

## 6. 单场比赛：协调、执行、恢复与赛后

### 6.1 比赛种类

| 类型 | 已有能力 | 影响范围 |

| 测试赛 | 管理员在未结束的公开赛事选择两支已批准队伍、BO、先手方及双方操作人；创建时准备合法赛事名单、冻结七图图池及所需资格 | 不生成正式阶段节点，不推进赛事，不进入正式累计统计/竞猜/奖项候选；仍用真实人员和实际转播容量。详情/BP 可匿名凭链接访问，公开列表不列出且不被搜索索引。 |
| 无赛事独立比赛 | 领域层可用双方名称/标志、图池快照创建、开始、结束、补结果/更正，并生成独立转播文档 | 可以没有预报名人员、BP 或数据源；无赛事晋级关系。基线没有面向用户的约战创建入口；现有设备安装、赛程窗口和实时回传仍按赛事授权，不能据此宣称独立约战全链路已开放。 |

测试赛是可转发的演练，不是私密测试空间；独立比赛的底层能力不等于一个已经可用的用户产品流程。[E16](implementation-index.md#e16)

### 6.2 时间协商、转播与阵容

双方本届负责人提出未来且不晚于最晚完赛时间的时间 → 对方接受/拒绝/另行提议。每场仅一个待回应提议；同队负责人交接后也不能接受本队提议。管理员可明确指定时间。首次提议完整 24 小时无人回应且执行时仍距开赛至少 2 小时才可自动采纳；改期必须对方明确接受，之前原定时间继续有效。上述小时数是当前排期规则，不是由用户研究推出的必要值。[E12](implementation-index.md#e12)

可选官方转播时段有容量，提议可短暂预留，确认时重新检查，过期预留不保证名额。没有转播名额仍可自由约定合法时间。解说可在资格允许时认领，每场至多两人；尚未开始 BP/比赛、没有未关闭制作会话时可取消本人认领，否则由管理员处理。[E12](implementation-index.md#e12)、[E21](implementation-index.md#e21)

负责人从本届正式名单选本场五名首发和 BP 负责人；逐场仍执行校籍、竞技和纪律资格。未交阵容时，在 T−2h 或提前开始 BP 时尝试用本届合法预定主力补默认首发；缺少合法五人就明确阻塞。临近开赛的参与者自助改阵容关闭，由管理员晚改；实际开赛再次核对并定格，不能由当前长期成员代替。[E12](implementation-index.md#e12)

### 6.3 BP、实际开局与外部比赛

**Major 政策要求**：计划时间前 15 分钟开放开始确认，双方负责人均确认可开始；计划时间后默认 15 分钟宽限，之后合法单方请求可进入开赛流程；连续官方比赛等情况由政策处理额外宽限。高种子/预排名方先选 VETO A/B，45 秒；正式 BP 负责人来自首发。[E01](implementation-index.md#e01)、[E13](implementation-index.md#e13)

| BO | 禁选/地图结果 | 计时与选边 |
| --- | --- | --- |
| BO1 | A 禁 2、B 禁 3、A 禁 1，剩余一图 | 连续禁图共用 60/75/45 秒；B 45 秒选边 |
| BO3 | A/B 各禁 1，A 选首图、B 选第二图，B/A 各禁 1，剩余决胜图 | 人工步骤各 45 秒；对方为所选地图选边，B 选决胜图起始边 |
| BO5 | A/B 各禁 1，再 A/B/A/B 交替选四图，剩余第五图 | 人工步骤各 45 秒；对方选边，第五图游戏内刀局决定 |

超时由系统从合法选项随机完成剩余选择，已完成步骤保留；技术原因可申诉并由管理员裁定、暂停/恢复。恢复有原因与当前版本核验；真实开图或正式地图结果后不再允许利用 BP 恢复更改赛前选择。已取消但未实际开图的比赛仍可由管理员说明后结束申诉，不恢复比赛。申诉自动关闭的写入开关在本基线尚关闭，详见第 11 节；不能把“支持读取已关闭状态”说成已经自动产生该状态。[E13](implementation-index.md#e13)

**业务契约**：BP 开始可令比赛进入进行中；BP 完成只确定地图与选边，不证明游戏已开局。真实对局/地图开始是单独且不可因回退清除的事实，也用于关闭观赛参与窗口。[E13](implementation-index.md#e13)、[E14](implementation-index.md#e14)

工作人员依据本站名单、地图顺序和起始边在完美平台人工建房与核对，RivalHub 不保存“外部房间已创建”的真相。游戏内战术暂停、技术暂停和回档属于完美平台/裁判执行；Major 政策规定每图每队 3 次战术暂停、每加时额外 1 次、默认累计技术暂停 15 分钟，不能把这些政策写成本站已经自动计数执行的能力。Mizar 设备、CS2 采集和 OBS 制播在外部工具完成。[E01](implementation-index.md#e01)、[E15](implementation-index.md#e15)

### 6.4 赛果与更正

正常正式比赛：合法阵容 → BP 地图计划 → 实际开局 → 逐图正式回合比分 → 达到 BO 胜场数 → 正式系列赛结果 → 相应赛事推进。BO1/3/5 分别需要 1/2/3 图胜利；系列比分与单图回合数分别表达。人工录入和校验通过的机器事件进入同一正式结果流程。[E14](implementation-index.md#e14)

弃赛/判负需明确输方与原因，是已结束比赛的一种结果，不虚构未打地图；取消不是有胜者的结果。Play-in 不允许单独取消或删除导致资格赛轮次断裂，裁决用正式弃赛结果。未打决胜图不产生待采集计分板/Demo 任务。[E14](implementation-index.md#e14)

结果更正必须核对旧版本并记录原因，不能覆盖当前事实；已完成单图、已结束系列赛、影响胜者/后续赛程的更正有不同边界。若更正使进行中系列应当已结束，专用预览会核验后续地图尚未实际开始、无已写资料、无阻塞的后续赛程/阶段/最终结果，再明确确认恢复。已开赛/已结束下游不能自动回滚；进入人工事故裁决。资格赛更正还要求正赛参赛方尚未产生，后续资格赛均未开始；允许时作废后续轮并重算。[E14](implementation-index.md#e14)

测试赛/无赛事比赛可结束为“已记录结果”“待补结果”“明确不提交结果”，后两种比分为空，不能展示为 0:0 或弃赛。结束、补录、更正分别操作；补录不重开执行、不改变首次结束时间，总比分不能与已知单图冲突。正式赛事不允许通过无结果结束绕过晋级。[E16](implementation-index.md#e16)

### 6.5 LIVE、计分板、Demo 与制作资料

Mizar 从本站获赛事级设备授权后读取比赛上下文；一场仅一个有效现场数据源，换机、切来源、切地图或人工接管会重新核验自动写赛果资格。可靠事件是候选证据，地图身份/名单/顺序/权限不一致时保留核对状态，不覆盖正式结果。没有 Mizar 时可正常走人工赛务；连接失鲜也不等于正式比分失效或自动授权手工改分。[E15](implementation-index.md#e15)

公众可看符合条件的实时计分板/雷达及已有直播嵌入，实时观察与正式比分分别呈现。已开始的正式 Play-in 和测试赛有早于正赛开始的 LIVE 资格；详情见 C02。断线、重连、暂未收到数据和已核验数据源不是同一状态；旧画面不能伪装为正在直播。[E15](implementation-index.md#e15)

地图正式完成后可 OCR 或手工补基础计分板，要求十名有效首发完整且唯一地匹配、字段和回合上下文合法。DAK 已确认的身份/游戏事实不被 OCR 覆盖，OCR 可补平台 Rating Pro、RWS、WE。DAK 上传经授权、身份/比分/语义版本核验后确认或待处理；更改阵容/比分/身份可能使旧证据需重新核验。管理员可确认可证明的替代 Steam 游戏身份，保留来源、原因与撤销边界，不改变登录身份。[E15](implementation-index.md#e15)

正式完赛不等待 OCR、DAK 或录像。图间可同时补上一图资料、准备下一图；赛后完整度分别取实际完成地图的计分板与 Demo、解说名单和录像事实。登记解说默认作为实际名单，保存录像后制作资料可就绪；明确重开解说名单更正后需再次确认，不因上传自动完成。录像链接/直播间与 Demo 证据不是同一种内容。[E21](implementation-index.md#e21)

## 7. 观赛参与、奖项与纪律

当前这些观赛参与入口面向 Major，不能将其描述为任意 Rivals/自定义比赛均可用。免费单场预测正常正赛要求关联 Major 阶段运行；报名期 Play-in 要求关联已开始且未完成的资格运行。上述产品不能因为中文都称“预测/竞猜”而合并其身份、截止和奖励含义。Pick’Em 只有正式 Main Event 提交；自由推演可覆盖符合条件的 Short Swiss Play-in，假想结果不填入正式提交名单。[E18](implementation-index.md#e18)、[E19](implementation-index.md#e19)、[E20](implementation-index.md#e20)

Pick’Em 当前 Swiss 选择 2 个全胜、6 个晋级、2 个全负队，淘汰赛选择全部 7 场胜者；纪念币按阶段挑战容量和固定门槛派生，独立于官方选手荣誉。免费预测命中榜至少一场有效已判定赛果即可排名，命中率榜另有样本资格线，未判定不伪造 0% 命中率。[E18](implementation-index.md#e18)、[E19](implementation-index.md#e19)

BET 当前积分没有现实货币价值；初始 1000 分，符合加入时间条件的后续正赛阶段补给 300 分，不补发 Play-in 或加入之前的阶段。有效已验证账户可主动领低保：非负且低于 10 时补到目标、北京时间每天一次、每届累计不超过 100，暂停/结束/负债等不允许；读取页面不自动开户或发分。这些数值均为当前产品政策实现，不是未来商业模型。[E20](implementation-index.md#e20)

BET 包含冠军/击杀王、比赛胜者/精确比分/总地图数、BP 和单图市场。BO3 新 BP 市场七选一，最终 BP 三图共享奖池、三图都为中奖选项，不要求决胜图实际进行；旧市场保留旧条款。总回合可按赛前图序开池，BP 后只补地图名，已冻结线不随排期或奖池变化。当前正式名单成员不能投涉及本队的市场，管理员身份本身不禁止参与。[E20](implementation-index.md#e20)

整数奖池无抽水，无胜方投入或全池获胜则退款。更正可能冲销已经花掉的收益，形成待抵扣负债，不可用手改余额消除。管理员能暂停/恢复、永久提前锁盘、说明原因作废退款及重试结算；不能编辑答案、赔率、选项或余额。暂停不停止结算，也不重开永久关闭的窗口。[E20](implementation-index.md#e20)

### 7.2 MVP、社区奖、官方荣誉

单场 MVP 由账号注册满 24 小时的登录用户在完赛后 24 小时内投票，每人每场一票；候选为已确认首发，旧赛史可回退到已核验统计中的选手；系统在截止后结算。单场票选 MVP 不自动成为 Major 官方 MVP 荣誉。[E21](implementation-index.md#e21)

社区奖由用户提出名称、达成条件和奖品 → 管理员审核/要求补充 → 公开后提交候选/比赛/视频证据 → 管理员结奖、不颁或取消，并可更正结论。发起人可在指定状态撤回；需赛事启用社区奖能力，**已归档赛事不能新提奖项**，因此不能将“跨阶段能力”读成所有状态下全部操作都开放（C03）。仓库只证明奖品描述及结奖记录，不证明现实奖品已履约。[E22](implementation-index.md#e22)

官方荣誉按已确认最终结果、明确手动奖项或裁决授予，可有效、撤销、空缺、不颁；撤销不自动递补。社区奖、官方名次/荣誉、MVP 票选、预测纪念币有不同依据和责任人。[E22](implementation-index.md#e22)

### 7.3 纪律与事故裁决

纪律案件区分草稿、生效、过期、撤销，可明确阻止报名、入名单或比赛出场，保存公开说明与内部证据。只有明确效果和有效时间窗内的处罚才执行；内部证据不公开。处罚与比赛判负、赛果更正、最终名次和荣誉撤销分别处理，不能根据“被禁赛”自动抹掉历史。[E22](implementation-index.md#e22)

Major 政策还涉及反作弊、代打/借号、真实 Steam 身份、第一视角录像、比赛中暂停/回档和赛委会复核。这些有人工及外部平台环节；本站有记录、约束和裁决能力，不等于能自动检测作弊或保证外部证据真实。[E01](implementation-index.md#e01)、[E22](implementation-index.md#e22)

## 8. 公开信息、历史与统计

公众可发现公开赛事及历史、阅读全站/赛事公告与规则、查看报名和参赛信息、赛程、结果、队伍与选手档案。资料不完整、未开赛、未定排期、无统计样本是有效状态；不能制造默认段位、已确认人数、比赛时长或缺失赛果。[E17](implementation-index.md#e17)、[E23](implementation-index.md#e23)

统计范围可按平台全部公开历史或单届、阶段、BO、地图、队伍等选择，覆盖战绩、记分板指标、细化表现、纪录和条件分析。选手按人归集；长期 Team 只归集明确关联的历史参赛方，不能把现成员的整个生涯拼成该队历史。赛事原生队保留独立身份；测试赛排除正式累计统计。有效首发出场、已完成地图、正式结果及已核验 DAK 覆盖各有范围，缺失细化资料会降低覆盖，不能以零填补。[E17](implementation-index.md#e17)

Rating/RWS/WE、ADR、爆头率、队伍 Rating 等指标具有各自分母/权重，不能因同在表格内而假定简单平均。样本不足者与满足资格的排名对象区分，未知阶段不静默扩大到全赛事，纪录并列保留。当前缓存与统计投影是可重建的实现选择；源证据版本、更正和身份归并对统计归属的约束是业务含义。[E17](implementation-index.md#e17)

赛事管理可维护公开 Logo、规则入口、群信息/二维码、公开联系人；全站/赛事公告分草稿与已发布，可撤下及标注关注期限。群二维码/公开联系人不让用户账号中的私人 QQ/邮箱自动公开。反馈允许匿名或登录提交问题、疑问、建议、纠错等，附最小页面路径与版本，平台运营标记待处理/处理中/已处理；不等于已有用户可跟踪的客服工单或保证回复时效。[E23](implementation-index.md#e23)

## 9. 关键状态与跨流程约束

状态必须与所属对象一起理解；下面是面向业务的摘要，不是让未来产品照搬字段或标签。每条具体操作仍有身份、窗口、版本和关联事实检查。[E07–E24](implementation-index.md)

| 对象 | 当前关键状态 | 不可误读之处 |
| --- | --- | --- |
| 赛事 | 草稿、报名、投票、选秀、比赛、结束、归档 | 报名状态内仍有待排、未到时、已开放、已截止；计划到时不等于 Major 开赛。 |
| 教育主张 | 待审、通过、驳回 | 材料到期不撤销已通过事实；待审不算已认证。 |
| 长期队伍/成员/邀请 | 队伍活跃/解散；成员活跃/替补/离开；邀请待答/接受/拒绝/撤销/过期 | 接受长期邀请与确认本届参赛是两步。 |
| 本届报名 | 草稿、已提交、要求补正、候补、通过、拒绝、已撤回 | 撤回审核会回新草稿；通过不等于正式席位；状态不是批准任何名单修改的充分条件。 |
| 名单版本/成员确认 | 版本草稿/提交/批准/被替代；成员待确认/确认/拒绝/退出 | 新版本要重新检查，旧特批不能自动沿用；同届有效承诺唯一。 |
| 本届正式名单/本场阵容 | 名单准备中/确认/冻结；本场提交/确认 | 已冻结的历史出场保留原引用；存在预定主力不证明已实际出场。 |
| 资格与阶段 | 方案草稿/确认、资格赛开始/完成、正赛参赛方确认、种子确认、阶段运行/轮次确认/完成 | 这些不是同一条进度百分比；推进由真实比赛及冻结名单决定。 |
| 排期 | 未提议、待回应、已确认、改期待回应、非活动 | 改期未接受时原时间有效，24 小时沉默规则只用于满足条件的首次排期。 |
| 比赛执行 | 待进行、进行中、结束、取消 | 进行中可能仍在 BP/等待游戏；弃赛属于结束结果；正式赛不支持无结果绕过晋级。 |
| 比赛呈现 | 准备、待 BP、BP、待开局、游戏中、图间、赛后、取消 | 是多个事实的派生视图，不是新增可直接编辑的比赛状态。 |
| BP/申诉 | 未开始/运行/暂停/完成；申诉待处理/接受/驳回/已关闭 | 恢复效力终止与是否自动写已关闭分别控制；真实开局后不能恢复 BP。 |
| 数据源/资料 | 自动或人工、健康/需核对、接收中/失鲜；计分板不齐/齐备、Demo 待核对/确认/被替代 | 没数据源不是比赛失败；正式完赛不等待资料齐备，失鲜不授权改赛果。 |
| 独立/测试结果处置 | 已记录、待补、明确不提交 | 后两者没有比分，不当作平局；补录不重置首次结束时间。 |
| Pick’Em/免费预测/BET | 各自可提交/永久截止/待判定/已判定/失效或退款 | 时间锁、草稿/提交、虚拟积分和成就不是共享状态；官方更正可能改变判定但不重开窗口。 |
| 最终结果/荣誉/纪律 | 最终结果待确认/确认；荣誉有效/撤销/空缺/不颁；处罚草稿/生效/过期/撤销 | 任何连锁影响都需明确裁决，不自动递补。 |
| 公告/反馈 | 草稿/发布；待处理/处理中/已处理 | 撤下不等于删除历史；已处理不等于已回复用户或已匿名化。 |

**当前产品必须满足的业务正确性要求**可归纳为：

- 操作人、作用赛事/比赛/名单、权限与预期旧状态必须一起核验；多人同时操作、重复提交不能产生重复占位、重复选人、重复赛果或重复积分。
- 不同生命周期的资料分别保存：当前声明、当届冻结规则、批准名单、实际出场和结果更正历史不能互相冒充。
- 参赛、名单和晋级不能从显示名称、导航位置、榜单排序或“看起来已完成”的界面推断；缺失资格/来源保持阻塞或未知。
- 正式结果及必要的更正必须保留操作、理由、依据和影响；已有下游开始事实不能被普通恢复无痕抹掉。
- 公开信息、本人私有信息、赛事内部审核和平台级敏感证据分别可见；界面隐藏不能替代授权。
- 已接受的条款、预测截止和积分流水不能因延迟、重试、延期、更新页面或管理员改显示而被重写。

以上是延续当前业务语义时的约束，未指定页面数、导航层级、技术栈、组件、颜色、按钮位置或设备布局。数值规则仍以其适用政策/当届快照为准。

## 10. 数据使用和服务边界

可公开的是明确允许的昵称、游戏身份、队伍/参赛资料、赛果与统计等投影，不是数据库整行。邮箱、QQ、教育原材料、举报与内部纪律证据、设备凭据和个人积分流水均需限定访问；教育原始材料只允许超级管理员通过受保护入口短期读取，赛事管理员不自动获得。[E02](implementation-index.md#e02)、[E24](implementation-index.md#e24)

正式赛事、冻结名单、赛果、荣誉、裁决与积分流水长期可追溯；归档和凭据撤销不是数据删除。已完成教育审核材料按七天业务保留清理；加密恢复副本有单独最长三十天政策。未定义的账号删除/匿名化、长期待审材料、旧联系方式/草稿、Demo 原数据、已处理反馈和部分运行日志保留不能宣传为已实现统一删除。[E24](implementation-index.md#e24)

账号/认证邮件、数据存储与实时订阅依赖 Supabase；游戏与建房依赖完美平台；现场制播依赖 Mizar/CS2/OBS，赛后解析依赖 DAK，视频可涉及 Bilibili，OCR 依赖外部服务。第三方不可用时有待确认、重试、人工接管/补录等不同路径；源码与隔离测试不能证明外部配置、现场可靠性或服务可用性承诺。[E15](implementation-index.md#e15)、[E24](implementation-index.md#e24)
