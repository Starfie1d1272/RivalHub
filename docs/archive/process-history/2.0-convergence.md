## 产品与扩展结构

Rivals 与 Major 是当前平行的内置赛事体系。平台通过 `StageConfig`、`StagePlan`、`StageExecutor` 与 executor registry 保持扩展基础，使后续赛事形态可以在相同 contract 上接入。

2.0 的 active runtime support 由循环赛、单败、双败和 Major-managed Swiss 组成。历史实现保留在 Git history，3.0 的新增赛事在当前 contract 上按真实需求建立。

下一轮代码收敛开始前，创建 immutable historical tag `archive/pre-2.0-convergence-2026-08-29`，保存此阶段的可复核基线。

## 赛事创建体验

赛事创建入口统一提供 **Rivals**、**Major** 与 **自定义赛事**。标准模板由 canonical factory 生成 form state，管理员界面以中文业务语义展示配置。

`seasons.competitionTemplate` 是模板身份的持久 owner。编辑赛季时服务端以持久化模板为准：draft 状态的 Rivals/Major 每次保存都从 canonical factory 重新建立固定语义（registration mode、captain voting、draft、stage plan、affiliation rules、队伍规模与首发人数及固定报名策略），管理员可调整 positions、map pool 与名称/主题/时间等元数据；custom 赛事保留自身输入，不会被按形状重新识别为内置体系。非 draft 状态只接受元数据修改，核心配置（包括 Major 冻结的竞技档案上下文）不会被改写。

custom tournament 的 hard gate 在 `publishSeason` 执行 `validateCompetitionDefinition()`：阶段支持由 active executor registry（`isStageExecutorSupported`）决定，当前为循环赛、单败淘汰与双败淘汰；晋级人数按 `tier.count × groupCount` 计算。draft 阶段允许保存未完成的配置，publish 才是可运行性关卡。

## Team registration policy

Major affiliation policy 由 `affiliationRules` 表达：home institution 为南京大学，eligible statuses 为 `enrolled`、`graduated`，minimum roster home members 与 minimum starting home members 均为 3。

`TeamRegistrationConfig` 的过渡计划遵循清晰 owner：

| 配置 | 长期 owner |
|---|---|
| `allowExternal`、`graduateCountsAsHome`、`minHomeMembers`、`minEnrolledMembers`、`maxExternalMembers` | `affiliationRules` |
| `requirePositions`、`maxPerPositionPerTeam` | 未来 PositionPolicy |
| `captainCanKick` | application member workflow |
| `lockAfterRegistration` | application state machine |
| `requireUniqueTeamName`、`requireTeamLogo`、competitive-profile requirement | 当前业务 consumer |

字段迁移按 runtime 停止读取、UI 停止写入、tests 证明无 consumer、migration 调整 owner 的顺序进行。当前管理界面（`TeamConfigForm`）只暴露仍由本层持有 runtime consumer 的配置：`captainCanTransfer`、`requireUniqueTeamName`、`requireTeamLogo` 与 `requireCompetitiveProfile`（后者仅提供平台结构化选择；current/previous season key 与 rank order 由全局目录在发布时冻结产生）。学校资格由 `affiliationRules` 表达，位置由 `season.positions` 表达，成员移除由 application 状态机表达。历史 JSON 中的旧键保持兼容读取，不做破坏性改写。

## Captain transfer

Application 阶段的 `captainUserId` 可转给当前 confirmed application member，原 captain 转为普通成员。approved/materialized team 阶段，`teams.captainUserId` 可转给正式 team member。Major entrant/final roster lock 后保留 admin emergency override。

每次 transfer 在事务内完成：锁定 application/team 行、重读当前队长、锁定 season lifecycle 行、`FOR UPDATE` 锁定目标成员（formal team 还会锁定存在的 Major entrant），全部 authority 与状态判断都基于事务内的锁定行。非管理员必须仍是当前队长、`captainCanTransfer` 为真、报名/注册窗口仍允许变更且名单未锁定；并发交接只有一个能按提交时的队长状态成功。UI 的交接入口仅对当前队长、super_admin、当前赛季授权的 season_admin 或 emergency Root 显示，并要求一次明确确认；action 是最终权限边界。每次 transfer 记录 audit。

## Long-lived participant facts

长期用户事实包括 display/profile、QQ、Steam identity、Perfect World identity、education verification 和 competitive rank facts。报名流程引用这些资料并保存必要的 event-time snapshot，避免把长期 profile 与一次赛事资料混为同一编辑域。

`competitivePlatformSeasons` 是竞技平台赛季目录，包含平台、赛季标识、显示名称、时间顺序、启用状态与当前赛季标记；platform + seasonKey 是目录项的不可变身份，编辑只允许 label、rank order、sort order、active 与 isCurrent，身份错误通过新建目录项更正。删除目录项前必须确认没有任何 rank fact 或已发布赛事冻结的竞技上下文引用该赛季，否则 fail closed。`competitiveRankFacts` 保存用户的 historical peak 与任意已编目平台赛季的 season peak 事实，参与者可以补录历史赛季资料。super-admin 在 `/admin/competitive-seasons` 管理目录，rank order/catalog ownership 独立于单届赛事配置。

发布赛事时，`publishSeason` 在事务内把全局目录的 current、previous 与 rank order 冻结进 `season.teamRegistrationConfig` 的 competitiveProfile。发布之后目录推进不影响已发布赛事的冻结上下文；empty draft 撤回（revert-to-draft）会解除 built-in 赛事的冻结，下一次发布从目录重新解析。event readiness 只检查该赛事冻结上下文要求的 exact season keys。

qualification 以 `src/lib/qualification/` 为单一 orchestration owner：batch fact loader（`loadParticipantQualificationFacts`、`loadEducationMembershipFacts`）配合既有 pure evaluators，提供 `getParticipantReadinessBatch` 与 `evaluateRosterQualification`；单用户 helper 内部走 batch 路径保持兼容。team application 提交、管理员审核、报名审核页、participant readiness 页与 Major prestart 的 live qualification 阶段都经由同一 owner，消除逐人 N+1。registration/application 读取 live facts，prestart 形成冻结事实，match 读取 frozen facts。

## Administration, privacy and education

正常管理员使用 Supabase Auth 与 `public.users.role`；`adminInvites` 是标准提权路径，`admin_users` 保持 emergency compatibility owner。

`user_sessions` / OnlineCounter 继续作为与 auth 独立的轻量活跃状态。

完整公共 `/privacy` 承载隐私说明。未来“隐私与数据”设置页在 data export、account deletion 或 public-field preference 等可操作能力形成后提供。

`institutions`、`institutionEmailDomains` 与 `educationVerifications` 继续作为教育事实模型。教育体验提供南京大学学生邮箱快速认证或学信网官方在线验证材料的清晰入口与说明。

## Positions and map pool

canonical positions 使用 `igl`、`awper`、`opener`、`closer`、`anchor`。position configuration 采用结构化添加、删除与排序/勾选，底层保持 `string[]` 以支持 custom extension。

map pool 属于赛事规则。管理界面采用结构化 map selector 与 custom map support；accessor、UI ownership 与 validation 先行统一，再按数据安全条件规划物理字段调整。

## Major format

标准 Major 界面展示赛事业务语义。赛事格式为：

| 阶段 | 赛制 |
|---|---|
| Stage 1 | 普通比赛 BO1；晋级/淘汰局 BO3 |
| Stage 2 | 普通比赛 BO1；晋级/淘汰局 BO3 |
| Stage 3 | 全部比赛 BO3 |
| Playoffs | Quarterfinal BO3；Semifinal BO3；Final BO5 |

该格式的政策 authority 是 [`../rules/nju-major.md`](../rules/nju-major.md)。

## Data lifecycle and operational safety

Schema 收敛以 audit、recovery、frozen snapshot、historical facts、transaction safety 与 integration tests 为基础。每一项 UI 配置必须有真实 consumer，每项规则必须有明确 evaluator，每项事实必须有唯一 owner。

`deleteSeason` 与 `revertSeasonToDraft` 共用 `assertSeasonHasNoHistoricalFacts` guard：赛季已产生报名、申请、正式队伍或比赛事实时 fail closed。空 draft 删除会清理未使用的管理员邀请与 `adminSeasonIds` 引用，audit FK 为 SET NULL，并写入全局 `season.deleted` 审计。对 requireCompetitiveProfile 的 built-in 赛事，revert-to-draft 同时解除发布时冻结的竞技上下文。完整 destructive lifecycle acceptance 仍在独立 staging DB 完成，结束后 reset staging DB。
