# RivalHub 2.0 上线前模型收敛决策

**Status:** Accepted, pending implementation / partially implemented

**Purpose:** 指导 2.0 正式上线前最后一次代码收敛。
**Not:** 当前 runtime 实现说明；当前事实以 code、schema、active migrations、tests 与 active technical docs 为准。

## Product and extension direction

Rivals 与 Major 是当前平行的内置赛事体系。3.0 仍支持更多赛事形态，因此保留 `StageConfig`、`StagePlan`、`StageExecutor` 和 executor registry 作为 extension foundation。产品只维护有真实 current consumer 的 implementation；未来能力通过当前 contract 重新接入。

下一轮 code cleanup 前计划创建 immutable historical tag `archive/pre-2.0-convergence-2026-08-29`。本决策不创建 tag。

## Tournament templates

标准赛事创建由 **Rivals template**、**Major template** 与 **自定义赛事**组成。模板的 canonical factory 产生 form state；UI 不再维护第二套 preset。管理员 UI 使用业务语义和中文文案，不把 Capability、Experimental 或 Advanced 作为产品标签。

现有 Rivals canonical preset 与 SeasonForm 手写 preset 的 drift 是后续 code convergence 项。

## Generic stage framework

保留通用 stage contract。标准 Rivals/Major UI 不直接暴露 `groupCount`、`advanceTiers`、`entrySeeds` 或 placement internals；这些由模板和业务语义拥有。

未来 custom tournament 在 publish/start 前必须统一执行 `validateCompetitionDefinition()` 并 fail closed。通用 executor 的最终产品支持范围在下一轮 code audit 确认；预计保留真正有价值的 round robin、single elimination 和 double elimination。Major Swiss 由 Major managed runtime ownership；generic Swiss、GSL 和 Open Tournament preset 从 active product support 中退役，历史实现由 Git 保留。

## Team registration policy ownership

后续退役 legacy `TeamRegistrationConfig` fields：`allowExternal`、`graduateCountsAsHome`、`minHomeMembers`、`minEnrolledMembers`、`maxExternalMembers`。政策统一由 `affiliationRules` 拥有。

当前 Major policy：home institution 为南京大学，eligible statuses 为 `enrolled`、`graduated`，minimum roster home members 为 3，minimum starting home members 为 3。不得使用 `0`、`99` 等 sentinel 表达政策。

以下字段在存在真实 owner 前退役：`requirePositions`、`maxPerPositionPerTeam`、`captainCanKick`、`lockAfterRegistration`。editable application 内的 remove member 是标准工作流，application state machine 是 mutability owner。`requireUniqueTeamName`、`requireTeamLogo` 与 competitive-profile requirement 保留给真实 consumer。

## Captain transfer

Captain transfer 是 2.0 accepted pending implementation：

- application 阶段，`captainUserId` 可转给当前 confirmed application member，原 captain 成为普通成员；
- approved/materialized team 阶段，`teams.captainUserId` 可转给正式 team member；
- Major entrant/final roster lock 后，用户不能自助转让，仅保留 admin emergency override；
- 每次 transfer 必须写 audit；若保留 `captainCanTransfer`，runtime 必须真正 enforce。

## Long-lived facts and qualification

长期用户事实包括 display/profile、QQ、Steam identity、Perfect World identity、education verification 和 competitive rank facts。赛事报名只维护 event-specific 信息，并在必要处保存 event-time snapshot；registration UI 引用 profile readiness，而不是复制另一个 profile editor。

`competitivePlatformSeasons` 是长期竞技赛季目录，`competitiveRankFacts` 是用户竞技事实。Major 以 current platform season、previous platform season 和 historical peak 引用它们；rank order/catalog ownership 应落在 platform configuration/versioning，后续补齐 super-admin 管理 UI。

qualification 收敛为 `qualification/` owner：`facts`、`participant`、`roster`、`lineup`、`policy`。共享 batch fact loaders 配合 pure evaluators；registration 使用 live facts，prestart 冻结 facts，match 使用 frozen facts，避免循环 `getParticipantReadiness(userId)` 造成 N+1。

## Administration and support boundaries

正常管理员是 Supabase Auth + `public.users.role`；`admin_users` 仅 emergency。后续删除普通 second-admin account creation path (`AdminRegisterForm` / `registerAdmin(username,password)`)，保留 `adminInvites` 为标准提权路径。

`user_sessions` / OnlineCounter 保留：它与 auth 边界独立、每用户状态小且低耦合。

完整公共 `/privacy` 保留。静态重复 `/settings/privacy` 在后续代码收敛中删除；仅当存在 data export、account deletion 或 public-field preference 等真实可操作设置时，再建立“隐私与数据”设置页。

Education 数据模型继续使用 `institutions`、`institutionEmailDomains` 与 `educationVerifications`。后续 UX 为南京大学学生邮箱快速认证或学信网官方在线验证材料提供更清晰入口与说明；这不是 Major rule 变更。

## Positions and map pool

canonical positions 保持 `igl`、`awper`、`opener`、`closer`、`anchor`。未来 position configuration UI 使用结构化添加、删除与排序/勾选，底层仍可使用 `string[]` 并保留 custom extension。

map pool 属于赛事规则而非 registration semantics。后续 UI 使用结构化 map selector 并支持 custom map；收敛先统一 accessor、UI ownership 和 validation，后续再考虑物理字段迁移，不进行危险 schema 大迁移。

## Major format

标准 Major UI 展示业务语义，隐藏 runtime internals。赛事格式已经确定：

| 阶段 | 赛制 |
|---|---|
| Stage 1 | 普通比赛 BO1；晋级/淘汰局 BO3 |
| Stage 2 | 普通比赛 BO1；晋级/淘汰局 BO3 |
| Stage 3 | 全部比赛 BO3 |
| Playoffs | Quarterfinal BO3；Semifinal BO3；Final BO5 |

该格式由赛事政策 authority 维护。

## Schema and deletion order

2.0 上线前不进行大规模 destructive schema rewrite。顺序为：runtime 停止读取 legacy field → UI 停止写入 → tests 证明无 consumer → 后续 migration drop 或移动 owner。

后续删除优先级是 duplicate owner、fake config、legacy UI、unused implementation、speculative implementation 和重复 validation/fact loading。必须保留 audit、recovery、frozen snapshot、historical facts、transaction safety 与 integration tests。目标是：one fact → one owner；one rule → one evaluator；every UI config → real consumer。

`deleteSeason` 对 Major/team-application data lifecycle 的完整性在下一轮 code audit 处理。完整 destructive test 使用 staging + reset database，不提供 production “一键彻底删除赛事”工具。
