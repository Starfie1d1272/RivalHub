# RivalHub 2.0 上线前模型收敛决策

**状态：** 已接受，分阶段实施

**适用范围：** RivalHub 2.0 上线前的模型与实现收敛。

**当前实现依据：** 代码、Schema、活动迁移、测试与 active technical docs。

## 产品与扩展结构

Rivals 与 Major 是当前平行的内置赛事体系。平台通过 `StageConfig`、`StagePlan`、`StageExecutor` 与 executor registry 保持扩展基础，使后续赛事形态可以在相同 contract 上接入。

2.0 的 active runtime support 由循环赛、单败、双败和 Major-managed Swiss 组成。历史实现保留在 Git history，3.0 的新增赛事在当前 contract 上按真实需求建立。

下一轮代码收敛开始前，创建 immutable historical tag `archive/pre-2.0-convergence-2026-08-29`，保存此阶段的可复核基线。

## 赛事创建体验

赛事创建入口统一提供 **Rivals**、**Major** 与 **自定义赛事**。标准模板由 canonical factory 生成 form state，管理员界面以中文业务语义展示配置。

custom tournament 在 publish/start 前执行 `validateCompetitionDefinition()`，以统一的 fail-closed 验证确认定义完整性。标准 Rivals/Major 界面将阶段分组、晋级层级、种子入口和名次细节封装在模板与业务语义中。

Rivals template 与 SeasonForm 的当前 preset 将收敛到同一 factory。

## Team registration policy

Major affiliation policy 由 `affiliationRules` 表达：home institution 为南京大学，eligible statuses 为 `enrolled`、`graduated`，minimum roster home members 与 minimum starting home members 均为 3。

`TeamRegistrationConfig` 的过渡计划遵循清晰 owner：

| 配置 | 长期 owner |
|---|---|
| `allowExternal`、`graduateCountsAsHome`、`minHomeMembers`、`minEnrolledMembers`、`maxExternalMembers` | `affiliationRules` |
| `requirePositions`、`maxPerPositionPerTeam` | 未来 PositionPolicy |
| `captainCanKick` | application member workflow |
| `lockAfterRegistration` | application state machine |
| `requireUniqueTeamName`、`requireTeamLogo`、competitive-profile requirement | 当前业务 consumer |

字段迁移按 runtime 停止读取、UI 停止写入、tests 证明无 consumer、migration 调整 owner 的顺序进行。

## Captain transfer

Application 阶段的 `captainUserId` 可转给当前 confirmed application member，原 captain 转为普通成员。approved/materialized team 阶段，`teams.captainUserId` 可转给正式 team member。Major entrant/final roster lock 后保留 admin emergency override。

每次 transfer 记录 audit。`captainCanTransfer` 如继续保留，必须由 runtime enforce。

## Long-lived participant facts

长期用户事实包括 display/profile、QQ、Steam identity、Perfect World identity、education verification 和 competitive rank facts。报名流程引用这些资料并保存必要的 event-time snapshot，避免把长期 profile 与一次赛事资料混为同一编辑域。

`competitivePlatformSeasons` 是竞技平台赛季目录，`competitiveRankFacts` 保存用户的 historical peak、previous platform season 和 current platform season 事实。后续提供 super-admin 的平台赛季管理 UI，使 rank order/catalog ownership 独立于单届赛事配置。

qualification 以 `qualification/` 的 facts、participant、roster、lineup、policy 为领域组织：共享 batch fact loaders 配合 pure evaluators；registration 读取 live facts，prestart 形成冻结事实，match 读取 frozen facts。

## Administration, privacy and education

正常管理员使用 Supabase Auth 与 `public.users.role`；`adminInvites` 是标准提权路径，`admin_users` 保持 emergency compatibility owner。

`user_sessions` / OnlineCounter 继续作为与 auth 独立的轻量活跃状态。

完整公共 `/privacy` 承载隐私说明。未来“隐私与数据”设置页在 data export、account deletion 或 public-field preference 等可操作能力形成后提供。

`institutions`、`institutionEmailDomains` 与 `educationVerifications` 继续作为教育事实模型。教育体验提供南京大学学生邮箱快速认证或学信网官方在线验证材料的清晰入口与说明。

## Positions and map pool

canonical positions 使用 `igl`、`awper`、`opener`、`closer`、`anchor`。position configuration 采用结构化添加、删除与排序/勾选，底层保持 `string[]` 以支持 custom extension。

map pool 属于赛事规则。管理界面采用结构化 map selector 与 custom map support；accessor、UI ownership 与 validation 先行统一，再按数据安全条件规划物理字段调整。

## Major format

标准 Major 界面展示赛事业务语义。赛事格式为：

| 阶段 | 赛制 |
|---|---|
| Stage 1 | 普通比赛 BO1；晋级/淘汰局 BO3 |
| Stage 2 | 普通比赛 BO1；晋级/淘汰局 BO3 |
| Stage 3 | 全部比赛 BO3 |
| Playoffs | Quarterfinal BO3；Semifinal BO3；Final BO5 |

该格式的政策 authority 是 [`../rules/nju-major.md`](../rules/nju-major.md)。

## Data lifecycle and operational safety

Schema 收敛以 audit、recovery、frozen snapshot、historical facts、transaction safety 与 integration tests 为基础。每一项 UI 配置必须有真实 consumer，每项规则必须有明确 evaluator，每项事实必须有唯一 owner。

`deleteSeason` 的 Major/team-application lifecycle 审计在下一轮代码工作中完成。完整 destructive test 在 staging 环境执行，结束后 reset staging DB。
